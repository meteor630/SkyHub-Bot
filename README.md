# Discord-бот SkyHub Aviation

Production-ready плагинный Discord-бот для сообщества **SkyHub Aviation**
(авиасимуляторы, пилоты, диспетчеры, любители авиации). Бот спроектирован
как долгоживущая платформа, а не одноразовый скрипт: ядро не нужно менять,
чтобы добавить новую функцию, плагины перезагружаются "на лету" без
остановки процесса, и падение одного плагина никогда не роняет остальных.

```
Discord  <-->  SkyHubBot (discord.py)
                 │
                 ├── PluginManager  ──загружает/перезагружает──>  plugins/*
                 │                                                   │
                 ├── EventBus  <───────публикация/подписка───────────┘
                 │
                 ├── PermissionService, ErrorHandler, I18n, TTLCache
                 │
                 └── Database (SQLAlchemy async) ──> PostgreSQL
```

## Архитектура

Три слоя, зависимости идут в одну сторону:

**Core → Services → Plugins**, а всё взаимодействие между плагинами идёт
через **Event Bus**, а не через прямые импорты друг друга.

| Компонент | Файл | За что отвечает |
|---|---|---|
| `BasePlugin` | `core/base_plugin.py` | Единственный интерфейс, который реализует каждый плагин: `setup()` / `start()` / `stop()`. |
| `PluginContext` | `core/plugin_context.py` | Единственный способ, которым плагин взаимодействует с ботом -- каждый cog, команда, подписка на событие и фоновая задача регистрируются здесь, чтобы их можно было автоматически освободить. |
| `PluginManager` | `core/plugin_manager.py` | Обнаруживает, загружает, разрешает зависимости и **безопасно перезагружает** плагины "на лету". |
| `EventBus` | `core/event_bus.py`, `core/events.py` | Асинхронная шина событий (pub/sub). Плагин никогда не импортирует другой плагин напрямую -- он публикует события/подписывается на них (`MemberJoined`, `ModerationAction`, `VoiceCreated` и т.д.). |
| `ErrorHandler` | `core/error_handler.py` | Любое исключение где угодно получает ID вида `ERR-ГГГГММДД-xxxxxx`, попадает в консольный лог и (с ограничением частоты) публикуется embed'ом в канал ошибок Discord. |
| `PermissionService` | `core/permissions.py` | Централизованное определение роли `OWNER > ADMIN > MODERATOR > SUPPORT > MEMBER > USER` -- ни один плагин никогда не хардкодит роль или ID пользователя. |
| `GuildConfigService` | `services/guild_config_service.py` | Определяет "в какой канал/какая роль" -- сначала `guild_settings` (настраивается вживую через `/setup`), затем `config.yaml` как запасной вариант. |
| `Database` | `database/database.py` | Асинхронная фабрика движка/сессий SQLAlchemy. Плагины никогда не держат сессию открытой -- используют `ctx.db.session()` как короткоживущий контекстный менеджер. |

### Почему это не разваливается при 30-50 плагинах

- **Ни один плагин не импортирует другой.** Всё сквозное поведение
  (например, плагин `audit`) строится через подписку на события, которые
  уже публикуют другие плагины -- добавление нового плагина не требует
  правок в существующих.
- **Ни один плагин не трогает `bot.add_cog` / `bot.tree.add_command`
  напрямую.** Всё идёт через `PluginContext` -- именно это делает
  возможной автоматическую горячую перезагрузку без утечек ресурсов, см.
  [Как устроена горячая перезагрузка](#как-устроена-горячая-перезагрузка).
- **Нигде нет захардкоженных ID.** Каналы/роли/категории определяются
  через `GuildConfigService`, настраиваются для каждого сервера прямо из
  Discord командой `/setup`.
- **Баг одного плагина не может уронить другой.** Обработчики Event Bus,
  фоновые задачи и slash-команды обёрнуты так, что исключения
  перехватываются, отправляются через `ErrorHandler` и никогда не
  попадают в основной цикл обработки событий Discord.

## Структура проекта

```
app/                     Точка входа процесса и тонкий подкласс Bot из discord.py
    main.py                 запуск через python -m app
    bot.py                  SkyHubBot(commands.Bot) + всегда включённые /status, /plugin
    lifecycle.py            восстановление при запуске + корректная остановка

core/                    Каркас, на котором строится каждый плагин
    base_plugin.py          контракт BasePlugin / PluginMeta
    plugin_context.py       отслеживаемая поверхность регистрации для плагина
    plugin_manager.py       обнаружение, граф зависимостей, безопасная горячая перезагрузка
    event_bus.py / events.py  внутренняя шина событий + датаклассы событий
    permissions.py          enum ролей + PermissionService + проверка @require()
    error_handler.py        центральный конвейер ошибок -> консоль + Discord
    command_registry.py     политика синхронизации slash-команд (тестовый сервер / глобально)
    scheduler.py            хелперы run_every / run_after для фоновой работы
    context.py              корреляция request_id/plugin/event через contextvars
    cli.py                  интерактивная консоль (перезагрузка плагинов, статус, ...)
    exceptions.py           общая иерархия исключений

database/
    database.py              фабрика асинхронного движка/сессий
    models/                  модели SQLAlchemy 2.x (один файл на сущность)
    repositories/            весь SQL живёт здесь -- плагины никогда не пишут запросы сами
    migrations/              окружение Alembic + версии (с поддержкой async)

services/                 Бизнес-логика, не привязанная к Discord, переиспользуемая между плагинами
    message_service.py      движок рендеринга Message Builder (embed'ы + разбиение на страницы)
    moderation_service.py   выполняет и записывает ban/kick/timeout/warn/unban
    voice_service.py        жизненный цикл временных голосовых каналов
    guild_config_service.py определение канала/роли: сначала БД, потом YAML

config/
    settings.py              секреты, только из .env (pydantic-settings)
    config.yaml               всё остальное: запасные ID каналов/ролей, переключатели плагинов
    loader.py                 объединяет config.yaml каждого плагина с корневым

logging_config/            красивый консольный лог + JSON-лог в файл (см. примечание ниже)
locales/                    ru.json / en.json -- см. utils/i18n.py
utils/                      небольшие независимые хелперы (разбиение текста, время, кэш, retry, i18n)

plugins/
    message_builder/         /message, /embed, /announce, /message_template
    moderation/               /mod ban|kick|timeout|warn|unban|history + захват через audit-log
    deleted_messages/         логирует содержимое удалённых сообщений
    edited_messages/          логирует изменения "до/после"
    member_logs/              логирование входов/выходов участников
    voice_channels/           временные приватные голосовые комнаты + управление владельцем
    welcome/                  приветственное сообщение через message_service
    audit/                    /audit -- единый таймлайн по пользователю, питается от Event Bus
    server_setup/             /setup -- настройка каналов/ролей прямо из Discord
    status_dashboard/         живой embed со статусом бота/плагинов в отдельном канале
    radio/                    /radio -- непрерывное радио из загруженных треков в голосовом канале
    aviation_profile/         /profile -- авиа-профиль участника (роль/симулятор/сеть) + выдача роли
    flight_log/                /flight -- личный бортжурнал пилота
    weather/                   /weather -- METAR/TAF по коду ICAO (aviationweather.gov)
    tickets/                   /ticket -- приватные каналы обращений в поддержку
    leveling/                  /level, /leaderboard, /rep -- XP, уровни, репутация
    flight_events/             /event -- совместные вылеты сообщества
    server_stats/              /server stats -- сводная статистика сервера

tests/                      pytest + pytest-asyncio; см. раздел «Тестирование»
```

> **Про имя пакета:** в ТЗ предлагался пакет верхнего уровня `logging/`.
> Это перекрыло бы стандартный модуль Python `logging` для каждого
> `import logging`, как только корень проекта попадёт в `sys.path`,
> поэтому здесь для той же задачи используется `logging_config/`.

## Установка на сервер с нуля

Ниже -- полная инструкция для случая, когда на сервере вообще ничего не
установлено. Есть два пути: **через Docker** (проще всего, рекомендуется)
и **вручную** (venv + systemd). Примеры команд -- для Ubuntu/Debian; для
других дистрибутивов замените менеджер пакетов.

### Вариант A. Через Docker (рекомендуется)

Docker сам поднимет и бота, и PostgreSQL в контейнерах -- отдельно
устанавливать Python или базу данных не нужно.

**1. Установите Docker и Docker Compose**, если их ещё нет:

```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
```

После этого перезайдите в SSH-сессию (или выполните `newgrp docker`),
чтобы применилось членство в группе `docker`.

**2. Установите git** (если ещё не установлен):

```bash
sudo apt update && sudo apt install -y git
```

**3. Склонируйте проект на сервер:**

```bash
git clone <адрес-вашего-репозитория> skyhub-bot
cd skyhub-bot
```

**4. Создайте файл `.env`** на основе примера и заполните токен бота:

```bash
cp .env.example .env
nano .env
```

Минимально нужно заполнить `DISCORD_TOKEN` (как его получить -- см.
[«Настройка бота в Discord»](#настройка-бота-в-discord) ниже).
`DATABASE_URL` для Docker-варианта переопределяется автоматически внутри
`docker-compose.yml` и указывать его в `.env` не обязательно.

**5. Запустите бота:**

```bash
docker compose up --build -d
```

Флаг `-d` запускает бота в фоне. Посмотреть логи:

```bash
docker compose logs -f bot
```

**6. Примените миграции базы данных** (один раз, при первом запуске):

```bash
docker compose exec bot alembic upgrade head
```

**Обновление бота после изменений в коде:**

```bash
git pull
docker compose up --build -d
docker compose exec bot alembic upgrade head   # если появились новые миграции
```

**Остановка бота:**

```bash
docker compose down
```

Docker Compose уже настроен на `restart: unless-stopped` -- бот сам
поднимется заново после перезагрузки сервера или падения процесса.

### Вариант B. Вручную (Python + systemd)

Используйте этот способ, если Docker недоступен или вы хотите
устанавливать зависимости напрямую на сервер.

**1. Установите Python 3.12+ и PostgreSQL:**

```bash
sudo apt update
sudo apt install -y python3.12 python3.12-venv python3-pip git \
    postgresql postgresql-contrib libpq-dev build-essential ffmpeg
```

Если в вашем дистрибутиве нет пакета `python3.12` из коробки, добавьте
PPA `deadsnakes` (Ubuntu) или соберите Python из исходников -- версия
должна быть 3.12 или новее. `ffmpeg` нужен только плагину `radio`
(декодирует аудио при воспроизведении в голосовом канале) -- если
радио вам не нужно, можно пропустить, но тогда отключите плагин
`radio` в `config/config.yaml` (`plugins.radio.enabled: false`),
иначе он будет писать ошибки в лог при каждой попытке что-то сыграть.

**2. Создайте базу данных и пользователя PostgreSQL:**

```bash
sudo -u postgres psql -c "CREATE USER skyhub WITH PASSWORD 'ваш_надёжный_пароль';"
sudo -u postgres psql -c "CREATE DATABASE skyhub OWNER skyhub;"
```

**3. Склонируйте проект:**

```bash
git clone <адрес-вашего-репозитория> skyhub-bot
cd skyhub-bot
```

**4. Создайте виртуальное окружение и установите зависимости:**

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

**5. Настройте `.env`:**

```bash
cp .env.example .env
nano .env
```

Укажите:
```
DISCORD_TOKEN=ваш_токен_бота
DATABASE_URL=postgresql+asyncpg://skyhub:ваш_надёжный_пароль@localhost:5432/skyhub
```

**6. Примените миграции базы данных:**

```bash
alembic upgrade head
```

**7. Проверьте, что бот запускается:**

```bash
python -m app
```

Если всё настроено правильно, в консоли появится приветственный текст
и строка вида `SkyHub Bot полностью запущен`. Остановить -- `exit` в
консоли или `Ctrl+C`.

**8. Настройте автозапуск через systemd**, чтобы бот работал постоянно
и поднимался заново после перезагрузки сервера или сбоя:

```bash
sudo nano /etc/systemd/system/skyhub-bot.service
```

Содержимое файла (замените пути и имя пользователя на свои):

```ini
[Unit]
Description=SkyHub Aviation Discord Bot
After=network.target postgresql.service

[Service]
Type=simple
User=ваш_пользователь
WorkingDirectory=/путь/к/skyhub-bot
ExecStart=/путь/к/skyhub-bot/.venv/bin/python -m app
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Затем:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now skyhub-bot
sudo systemctl status skyhub-bot        # проверить, что запустился
journalctl -u skyhub-bot -f             # смотреть логи в реальном времени
```

**Обновление бота после изменений в коде:**

```bash
cd skyhub-bot
git pull
source .venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
sudo systemctl restart skyhub-bot
```

## Настройка бота в Discord

**1. Создайте приложение и бота** в
[Discord Developer Portal](https://discord.com/developers/applications):

- «New Application» -> дайте имя (например, SkyHub Bot).
- Слева откройте вкладку **Bot** -> «Reset Token» -> скопируйте токен
  и вставьте его в `.env` как `DISCORD_TOKEN`. Токен показывается только
  один раз -- если потеряли, сбросьте заново.
- На той же вкладке **Bot** включите три переключателя в разделе
  **Privileged Gateway Intents**:
  - **Server Members Intent** -- нужен плагинам `member_logs`,
    `moderation`, `voice_channels`.
  - **Message Content Intent** -- нужен плагинам `deleted_messages`,
    `edited_messages`, `message_builder`.
  - **Presence Intent** -- не обязателен, но не помешает включить.

Без этих переключателей бот подключится, но соответствующие события
Discord просто не будут приходить -- это самая частая причина, почему
"логи не пишутся".

**2. Сгенерируйте ссылку приглашения** во вкладке **OAuth2 -> URL
Generator**:

- **Scopes:** отметьте `bot` и `applications.commands` (второй нужен для
  slash-команд).
- **Bot Permissions:** проще всего выдать **Administrator** -- бот
  является ядром модерации сервера и так или иначе использует бан, кик,
  тайм-аут, управление каналами, ролями и правами. Если хотите выдать
  права точечно, минимальный набор: `Manage Roles`, `Manage Channels`,
  `Kick Members`, `Ban Members`, `Moderate Members`, `Manage Messages`,
  `Manage Nicknames`, `Move Members`, `Connect`, `View Audit Log`,
  `Send Messages`, `Embed Links`, `Attach Files`, `Read Message History`,
  `Use Application Commands`.
- Скопируйте получившуюся ссылку внизу страницы, откройте её в браузере
  и добавьте бота на нужный сервер.

**Важно:** роль бота в списке ролей сервера (Server Settings -> Roles)
должна находиться **выше** тех ролей, которыми он будет управлять
(например, выше роли Moderator) -- иначе Discord не позволит боту
выдавать/снимать такие роли или банить их обладателей.

**3. Запустите бота** (см. раздел выше) -- при первом успешном
подключении он зарегистрирует свои slash-команды. Глобальная
регистрация может занять до часа, чтобы команды появились у всех
пользователей; для мгновенной проверки во время настройки укажите в
`.env` переменную `DEV_GUILD_ID` (ID вашего сервера) -- тогда команды
появятся на этом сервере сразу же после перезапуска бота.

Как узнать ID сервера: в Discord включите Режим разработчика
(Настройки пользователя -> Расширенные -> Режим разработчика), затем
щёлкните правой кнопкой по иконке сервера -> «Копировать ID сервера».

## Как пользоваться ботом

### Первоначальная настройка сервера

Как только бот на сервере и slash-команды зарегистрированы, зайдите под
аккаунтом с правом «Управление сервером» (или ролью, настроенной как
Admin) и выполните:

```
/setup channels
```
Появится сообщение с выпадающими списками -- выберите текстовый канал
для каждого типа логов: логи модерации, удалённые сообщения, изменённые
сообщения, вход/выход участников, ошибки бота. Каждый выбор сохраняется
мгновенно, ничего перезапускать не нужно.

```
/setup voice
```
Выберите: канал для приветственных сообщений, категорию, в которой
будут создаваться временные комнаты, обычный голосовой канал
«создать комнату» (без лимита участников) и, по желанию, один-два
**быстрых создателя** -- отдельные голосовые каналы, заходя в которые
участник сразу получает комнату с готовым лимитом на 2 или на 4 места
(не нужно потом выставлять лимит командой `/voice limit`). Все эти
голосовые каналы и категорию нужно создать в Discord заранее вручную --
бот их не создаёт сам, только использует.

```
/setup roles
```
Выберите роли Discord, которые соответствуют уровням доступа бота:
Администратор, Модератор, Поддержка. Участник с правом Discord
"Administrator" или являющийся владельцем сервера автоматически
получает наивысший уровень доступа независимо от этой настройки.

```
/setup status
```
Выберите текстовый канал, в котором бот будет держать одно постоянно
обновляемое сообщение со своим статусом (см.
[«Живой статус бота»](#живой-статус-бота) ниже).

```
/setup radio
```
Выберите голосовой канал, где будет играть радио, и текстовый канал
для сообщения "сейчас играет" (см.
[«Радио»](#радио-непрерывное-воспроизведение-музыки) ниже). Если радио
не нужно -- просто не настраивайте этот пункт, плагин ничего не будет
делать без сконфигурированного голосового канала.

```
/setup ignored-roles
```
Выберите роли (можно несколько, можно ни одной), выдачу и снятие
которых **не нужно** писать в лог модерации -- удобно для
самовыдаваемых/массовых ролей (симулятор, регион и т.п.), которые
иначе заваливают канал логов сотнями записей в день. Значимые роли
(например, Модератор) можно оставить залогированными, исключив только
шумные.

```
/setup flights
```
Выберите текстовый канал, в который бортжурнал будет публиковать
карточку каждого залогированного рейса (см.
[«Бортжурнал»](#бортжурнал-flight-logging) ниже).

```
/setup tickets
```
Выберите категорию Discord, в которой будут создаваться приватные
каналы обращений в поддержку (см.
[«Тикеты поддержки»](#тикеты-поддержки) ниже). Категорию нужно создать
в Discord заранее вручную.

```
/setup profile-roles pilot:<роль> atc:<роль> virtual_airline:<роль> flight_simmer:<роль> spotter:<роль> enthusiast:<роль>
```
Свяжите каждый тип авиа-профиля (см.
[«Авиа-профиль участника»](#авиа-профиль-участника) ниже) с ролью
Discord, которая будет выдаваться автоматически при выборе этого типа
и сниматься при смене на другой. Все параметры необязательны и
независимы -- можно указать один, часть или все сразу, повторный
вызов лишь дополняет/обновляет уже сохранённые связи, а не сбрасывает
их.

```
/setup channel key:<пункт> channel:<#канал или ID>
```
Запасной способ задать канал/категорию напрямую, если подходящих
каналов на сервере больше 25 -- список выбора (см. ниже) физически не
может показать больше в одном выпадающем меню. Эта команда принимает
канал как обычный параметр команды, поэтому лимита в 25 у неё нет.
`key` -- выпадающий список всех пунктов, что настраиваются через
`/setup channels`, `voice`, `status`, `radio`, `flights`, `tickets`
(например `moderation-logs`, `radio-voice`, `tickets-category`).

```
/setup role key:<пункт> role:<@роль>
```
То же самое, но для ролей модерации (`admin`, `moderator`, `support`) --
запасной способ задать роль напрямую по упоминанию, если она не
появляется в списке выбора у `/setup roles`.

```
/setup ignore-role role:<@роль> ignored:<true/false>
```
Добавляет или убирает одну роль из списка исключений лога (см.
`/setup ignored-roles` ниже), не трогая остальные уже выбранные --
удобно, когда список роли слишком большой, чтобы через него было
удобно ставить крестики по одной.

> **Про списки выбора канала/роли:** списки в `/setup channels`,
> `voice`, `status`, `radio`, `flights`, `tickets`, `roles`,
> `ignored-roles` строятся не через нативные `discord.ui.ChannelSelect`/
> `discord.ui.RoleSelect`, а вручную -- напрямую из списка каналов/ролей
> сервера, который уже есть у бота (обновляется мгновенно при
> создании/удалении). У обоих родных компонентов на практике
> обнаружилась одна и та же проблема: они используют отдельный, не
> документированный механизм автозаполнения на стороне Discord, из-за
> которого часть каналов/ролей (в том числе свежесозданные) могла не
> появляться в списке даже при полностью корректных правах доступа.
> Ручной список от этой проблемы не зависит. Единственное ограничение --
> у обычного списка жёсткий лимит в 25 пунктов; если каналов/ролей
> подходящего типа больше, для «лишних» используйте `/setup channel`/
> `/setup role`/`/setup ignore-role` выше.

```
/setup show
```
Показывает текущую конфигурацию сервера -- все выбранные каналы, роли
и категории.

### Живой статус бота

Плагин `status_dashboard` держит в канале, настроенном через
`/setup status`, одно сообщение, которое сам же редактирует -- раз в
минуту и сразу же при изменении состояния любого плагина (загрузка,
перезагрузка, ошибка). Никакого спама новыми сообщениями: если
сообщение удалить руками, бот на следующем обновлении просто создаст
новое и запомнит его. В сообщении: статус бота, задержка до Discord,
статус базы данных, аптайм, число участников сервера и список всех
плагинов с их статусом и версией -- ровно то же самое, что показывает
`/status` и консольная команда `status`, только без необходимости их
вызывать.

### Радио -- непрерывное воспроизведение музыки

Плагин `radio` даёт голосовому каналу вашего сервера играть загруженные
треки по кругу, как радиостанция -- этого не было в исходном ТЗ, но
раз понадобилось, вот как это устроено:

```
/radio add track:<файл>
```
Прикрепите аудиофайл (`.mp3`, `.ogg`, `.wav`, `.m4a`, `.flac`, `.webm`,
до 25 МБ -- это лимит вложений Discord) -- бот сохранит его на диск
сервера (`data/radio/<ID сервера>/`) и добавит в конец плейлиста.

При добавлении бот сразу читает теги файла (название, исполнитель,
альбом, композитор, битрейт, длительность, обложка -- через
`mutagen`) и сохраняет их в базе. Карточка "сейчас играет" в канале,
настроенном через `/setup radio`, оформлена по этим данным: крупный
заголовок -- альбом/OST, жирным -- название трека, ниже -- список
технических полей и обложка из тегов. Если у файла нет тегов (например,
чистый `.wav`) -- карточка покажет то, что есть (как минимум имя файла
как название), просто без лишних полей. Разметить файлы тегами и
обложкой заранее можно любым тег-редактором (`Mp3tag`, `Kid3` и т.п.)
до загрузки через `/radio add`.

```
/radio list             -- показать плейлист (▶️ отмечает текущий трек)
/radio remove index:<n> -- удалить трек по номеру из /radio list
/radio play             -- подключиться к голосовому каналу и начать/продолжить радио
/radio skip             -- переключиться на следующий трек
/radio stop             -- остановить радио и отключиться от голосового канала
```

Если голосовой канал для радио настроен через `/setup radio` и в
плейлисте уже есть треки, бот сам подключится и начнёт играть при
каждом запуске -- вызывать `/radio play` вручную после перезапуска не
обязательно. Плейлист играет по кругу бесконечно, пока его не
остановят через `/radio stop`.

**Системные требования** (см. также
[«Установка на сервер с нуля»](#установка-на-сервер-с-нуля)): нужен
установленный в системе `ffmpeg` (декодирует аудио) и Python-пакет
`PyNaCl` (уже в `requirements.txt`, шифрует голосовое соединение). Без
них плагин `radio` сам напишет понятную ошибку при попытке что-то
сыграть, но не помешает работе остальных плагинов (ТЗ §23) -- через
`docker compose` оба уже входят в образ.

### Система прав доступа

У бота пять уровней доступа (по возрастанию): `USER` (гость/ЛС) <
`MEMBER` (участник сервера) < `SUPPORT` < `MODERATOR` < `ADMIN` <
`OWNER` (владелец сервера). Каждая команда требует минимальный уровень:
например, `/mod ban` требует `MODERATOR`, `/setup` -- `ADMIN`. Роль
считается по правилу «побеждает наивысшая»: владелец сервера и
администраторы Discord всегда проходят проверку, для остальных роль
берётся из настроек `/setup roles`.

### Как создавать и использовать голосовые каналы

**Для участников сервера:**

1. Зайдите в голосовой канал, который администратор назначил как
   «создать комнату» через `/setup voice` -- обычный (без лимита) или
   один из быстрых («на 2»/«на 4»).
2. Бот автоматически создаст для вас личную голосовую комнату в нужной
   категории (с уже готовым лимитом участников, если зашли через
   быстрый создатель) и переместит вас туда.
3. В текстовом чате внутри самой голосовой комнаты появится сообщение с
   кнопками управления:
   - 🔒 **Закрыть** / 🔓 **Открыть** -- запретить/разрешить всем заходить.
   - 👥 **Пользователи** -- показать список участников комнаты.
   - ✏️ **Название** -- открыть форму для переименования.
   - 👤 **Передать владельца** -- выбрать нового владельца из списка
     присутствующих в комнате.
   - 🗑 **Удалить** -- удалить комнату немедленно.
4. Те же действия доступны командами (можно использовать вместо кнопок):

```
/voice name <название>        -- переименовать комнату
/voice limit <число>          -- лимит участников (0 = без лимита)
/voice lock                   -- закрыть комнату
/voice unlock                 -- открыть комнату
/voice hide                   -- скрыть комнату из списка каналов
/voice show                   -- сделать комнату видимой
/voice kick <участник>        -- выгнать из комнаты
/voice ban <участник>         -- заблокировать доступ и выгнать
/voice allow <участник>       -- разрешить конкретному участнику заходить
/voice deny <участник>        -- запретить конкретному участнику заходить
/voice transfer <участник>    -- передать владение комнатой
```

5. Часть действий можно сделать и напрямую в интерфейсе Discord --
   владелец получает на свою комнату `Управление каналом` (переименовать,
   поменять лимит участников прямо в настройках канала) и `Управление
   голосовой связью` (отключить кого-то от разговора кликом/командой
   Discord). Вкладку **Разрешения** и заглушение микрофона участникам
   мы туда намеренно не выдаём -- заглушение микрофона в Discord
   привязано к участнику на весь сервер, а не к конкретному каналу, и
   осталось бы с ним даже после выхода из этой комнаты; для этого есть
   безопасная команда `/voice ban`, которая просто не пускает обратно,
   ничего не трогая за пределами комнаты.

Управлять комнатой (командами, кнопками или настройками канала) может
только её текущий владелец -- у остальных участников таких прав на
канал нет. Когда комната
пустеет, бот ждёт около 10 секунд (на случай, если кто-то просто
переключается между каналами) и затем удаляет её автоматически --
вручную удалять временные комнаты не нужно.

### Message Builder -- красивые сообщения

Доступно администраторам/модераторам/Support (в зависимости от
команды):

```
/message text:<текст> channel:<канал>
```
Отправляет обычный текст; если текст длиннее лимита Discord, бот сам
разобьёт его на несколько сообщений с пометкой `MESSAGE 1/3`, `2/3` и т.д.

```
/embed title:<заголовок> description:<текст> color:<hex, напр. 2B6CB0> image_url:<URL>
```
Отправляет оформленное сообщение (embed) с цветной полосой слева,
опциональной картинкой/GIF.

```
/announce
```
Открывает форму (заголовок + текст + картинка) для быстрого
объявления -- удобнее `/embed` для длинных текстов, так как поле ввода
многострочное.

```
/message_template template:<имя шаблона> channel:<канал>
```
Отправляет сообщение из готового YAML-шаблона (с разделами, автором,
подвалом, картинкой). Шаблоны лежат в
`plugins/message_builder/templates/*.yaml` -- чтобы добавить новый,
просто положите туда `.yaml`-файл, менять код не нужно. Пример
структуры -- в файле `welcome_example.yaml` в этой же папке.

### Модерация

Все команды модерации сохраняются в базу данных, публикуют красивый лог
в канал, назначенный через `/setup channels`, и видны в `/audit`:

```
/mod ban <участник> [причина] [delete_days]   -- забанить
/mod unban <ID пользователя> [причина]        -- разбанить
/mod kick <участник> [причина]                -- выгнать
/mod timeout <участник> <минуты> [причина]    -- выдать тайм-аут
/mod warn <участник> [причина]                -- выдать предупреждение
/mod history <участник>                       -- история модерации участника
```

Дополнительно бот сам замечает и логирует действия, сделанные
администраторами напрямую через интерфейс Discord (бан из списка
участников, изменение ролей, переименование каналов и т.п.) -- для
этого не нужно ничего включать отдельно, это работает через встроенный
audit-log Discord.

### Единый таймлайн участника

```
/audit <участник>
```
Показывает хронологию событий конкретного участника: вход/выход с
сервера, действия модерации, создание голосовых комнат и т.д. -- всё в
одном месте, удобно для расследования жалоб.

### Авиа-профиль участника

Идея «системы контекста пользователя» из финального пожелания клиента:
каждый участник может рассказать боту, кто он в авиационном сообществе,
а бот сам выдаёт за это роль Discord.

```
/profile set
```
Открывает форму с тремя выпадающими списками: тип профиля (пилот,
диспетчер/ATC, виртуальная авиакомпания, флайт-симмер, споттер,
энтузиаст), симулятор (MSFS, X-Plane, Prepar3D, DCS -- необязательно)
и онлайн-сеть (VATSIM, IVAO, PilotEdge -- необязательно). При нажатии
«Сохранить» бот запоминает профиль и, если для выбранного типа
настроена роль через `/setup profile-roles`, выдаёт эту роль (и
снимает роль предыдущего типа, если он менялся).

```
/profile show [участник]
```
Показывает сохранённый авиа-профиль -- свой или указанного участника.

### Бортжурнал (Flight logging)

```
/flight log
```
Открывает форму: самолёт, маршрут (в формате `ВЫЛЕТ-ПРИЛЁТ`, например
`UUEE-ULLI`), длительность (принимает `1:45`, `1ч45м`/`1h45m` или
просто число минут), сеть и VATSIM ID -- два последних поля
необязательны. После сохранения бот публикует карточку рейса в канал,
настроенный через `/setup flights`, и добавляет налёт к статистике
участника (см. [«XP, уровни и репутация»](#xp-уровни-и-репутация)).

```
/flight history [участник]  -- последние 10 залогированных рейсов
/flight stats [участник]    -- сколько всего рейсов и суммарный налёт
```

### Авиационная погода (METAR/TAF)

```
/weather metar icao:<код аэропорта>
/weather taf icao:<код аэропорта>
```
Запрашивает актуальную сводку с публичного API `aviationweather.gov`
(без ключа, без ограничений по региону -- работает для любого ICAO с
регулярными наблюдениями). `/weather metar` разбирает сырой текст на
понятные поля (ветер, видимость, облачность, давление, температура,
точка росы) и прикладывает исходный код; `/weather taf` показывает
прогноз в исходном виде -- полный разбор TAF на поля не делается,
формат слишком вариативен для надёжного парсинга.

### Тикеты поддержки

```
/ticket panel
```
(Только Admin.) Публикует в текущем канале панель с кнопкой «Создать
обращение» -- разовая настройка, кнопка остаётся рабочей и после
перезапуска бота.

Участник нажимает кнопку -- бот создаёт приватный текстовый канал
(видимый только автору, ролям поддержки и модерации) в категории,
настроенной через `/setup tickets`, и публикует в нём кнопку
«Закрыть». Не более 3 одновременно открытых обращений на одного
участника. Закрыть обращение может тот же, кто его создал, либо
поддержка/модерация -- командой `/ticket close` или кнопкой; канал
удаляется автоматически через несколько секунд после закрытия.

### XP, уровни и репутация

За каждое сообщение (не чаще раза в минуту на участника, чтобы нельзя
было накручивать спамом) начисляется опыт; уровень растёт по формуле
`уровень = ⌊√(опыт / 100)⌋`, о повышении бот сообщает прямо в канале,
где оно произошло.

```
/level [участник]       -- уровень, опыт, репутация, сообщения, налёт
/leaderboard             -- топ-10 сервера по опыту
/rep <участник>          -- выдать участнику 1 репутацию (раз в 24 часа)
```

Налёт в `/level` -- тот же самый, что копится через `/flight log`:
плагины `leveling` и `flight_log` не знают друг о друге напрямую и
связаны только через Event Bus, поэтому один из них можно отключить
без поломки другого.

### Совместные вылеты (Flight events)

```
/event create
```
Открывает форму: название события, маршрут, самолёт, дата/время в UTC
в формате `ГГГГ-ММ-ДД ЧЧ:ММ` (например `2026-09-05 20:00`) и лимит
участников (`0` -- без лимита). Бот публикует в текущем канале карточку
события с кнопками «✅ Участвовать» / «❌ Не участвовать»; счётчик
участников в карточке обновляется сразу при нажатии. Кнопки остаются
рабочими и после перезапуска бота.

```
/event list
```
Показывает ближайшие ещё не прошедшие совместные вылеты сервера.

### Статистика сервера

```
/server stats
```
Сводная карточка: число участников (всего и онлайн), число в голосовых
каналах, число рейсов и суммарный налёт по бортжурналу, число
засчитанных XP сообщений, открытые/закрытые тикеты и распределение
участников по типам авиа-профиля. Собирает данные всех остальных
фич этого раздела, не храня ничего своего.

### Статус и здоровье бота

```
/status
```
Показывает задержку до Discord, статус базы данных, сколько плагинов
запущено и аптайм. Доступно всем.

```
/plugin list | reload | enable | disable
```
То же самое управление плагинами, что и в консоли, но прямо из Discord
(требуется роль Admin).

## Работа с базой данных и миграциями

Изменения схемы проходят через Alembic, настроенный на тот же
асинхронный драйвер (`asyncpg`), что использует сам бот:

```bash
alembic upgrade head                                  # применить миграции
alembic revision --autogenerate -m "add xp table"      # создать новую миграцию
alembic downgrade -1                                   # откатить на шаг назад
```

При использовании Docker выполняйте эти команды через
`docker compose exec bot alembic ...`.

## Консоль управления (CLI)

При запуске `python -m app` в обычном интерактивном терминале доступна
консоль:

> **Важно:** консоль работает только если stdin -- настоящий терминал.
> При запуске как фоновый сервис (systemd без `StandardInput=tty`,
> `docker compose up -d`, любой запуск с перенаправлением из
> `/dev/null`) бот сам это определяет и просто отключает чтение
> консоли (одной строкой в логе), не пытаясь опрашивать закрытый stdin.
> В таком режиме управляйте ботом через `/status` и `/plugin` прямо в
> Discord, а логи смотрите через `journalctl -u skyhub-bot -f` (systemd)
> или `docker compose logs -f bot` (Docker). Если консоль всё же нужна
> при запуске через Docker -- `docker attach <контейнер>` к уже
> запущенному интерактивно (`stdin_open`/`tty` включены в
> `docker-compose.yml`) контейнеру.

```
SkyHub Bot -- консоль управления

  bot start | stop | restart

  plugin list
  plugin info <plugin>
  plugin enable <plugin>
  plugin disable <plugin>
  plugin reload <plugin>
  plugin restart <plugin>
  plugin status

  sync            -- опубликовать slash-команды глобально
  status          -- снимок состояния бота
  health          -- то же самое, что status
  logs            -- путь к файлу JSON-логов
  clear           -- очистить терминал
  help            -- эта справка
  exit / quit     -- корректная остановка бота
```

`plugin list` выводит таблицу как в ТЗ:

## Разработка новых плагинов

Плагин -- это папка внутри `plugins/` с файлом `plugin.py`,
предоставляющим переменную `PLUGIN_CLASS`. Это весь контракт, который
нужен `PluginManager`, чтобы его обнаружить (ТЗ §30) -- без изменений в
ядре.

```
plugins/
└── weather/
    ├── __init__.py
    ├── plugin.py        <- обязателен: PLUGIN_CLASS = WeatherPlugin
    ├── commands.py       (опционально) slash-команды
    ├── service.py         (опционально) бизнес-логика, тестируемая без discord.py
    └── config.yaml       (опционально) значения по умолчанию, объединяются с plugins.weather в config.yaml
```

### 1. Минимальный плагин

```python
# plugins/weather/plugin.py
from core.base_plugin import BasePlugin, PluginMeta

class WeatherPlugin(BasePlugin):
    meta = PluginMeta(
        name="weather",
        version="1.0.0",
        description="Получение METAR/TAF",
        author="Ваше имя",
        dependencies=(),          # напр. ("voice_channels",), если есть зависимость
    )

    async def setup(self) -> None:
        # регистрируйте cog'и/команды/слушатели здесь -- всегда через self.ctx
        pass

PLUGIN_CLASS = WeatherPlugin
```

Затем:

```
plugin enable weather
```

### 2. Добавление slash-команды

```python
import discord
from discord import app_commands
from discord.ext import commands

class WeatherCog(commands.Cog):
    def __init__(self, ctx):
        self.ctx = ctx

    @app_commands.command(name="metar", description="Получить последний METAR для аэропорта")
    async def metar(self, interaction: discord.Interaction, icao: str) -> None:
        await interaction.response.send_message(f"METAR для {icao.upper()}: ...")

# в WeatherPlugin.setup():
await self.ctx.add_cog(WeatherCog(self.ctx))
```

Именно `ctx.add_cog` (а не `self.ctx.bot.add_cog`) позволяет менеджеру
плагинов автоматически удалить cog -- и все команды/слушатели в нём --
при перезагрузке/выгрузке.

### 3. Публикация событий и подписка на них

```python
from core.events import Event
from dataclasses import dataclass

@dataclass(frozen=True, kw_only=True)
class MetarFetched(Event):
    icao: str

# публикация (из любого места, где есть доступ к ctx):
self.ctx.emit(MetarFetched(guild_id=interaction.guild_id, icao=icao))

# подписка (обычно в setup() другого плагина):
self.ctx.subscribe(MetarFetched, self._on_metar_fetched)
```

Обработчики изолированы: исключение в вашем обработчике перехватывается,
передаётся в `ErrorHandler` и не влияет на других подписчиков.

### 4. Добавление модели базы данных

1. Добавьте модель в `database/models/your_model.py`, зарегистрируйте её
   в `database/models/__init__.py`.
2. Добавьте репозиторий в `database/repositories/` -- плагины никогда не
   пишут SQL/ORM-запросы сами, только через репозиторий.
3. Выполните `alembic revision --autogenerate -m "add your_model"` и
   проверьте сгенерированную миграцию перед коммитом.
4. Используйте из плагина через `async with self.ctx.db.session() as session:`.

### 5. Горячая перезагрузка

Просто отредактируйте файлы плагина и выполните:

```
plugin reload weather
```

Что именно при этом происходит и что должен гарантировать ваш плагин --
см. раздел [Как устроена горячая перезагрузка](#как-устроена-горячая-перезагрузка).

### 6. Обработка ошибок

Не глотайте исключения молча и не позволяйте им ронять слушатель.
Либо дайте исключению всплыть из метода cog'а (discord.py направит его
в общие обработчики `on_app_command_error`/`on_error`, которые уже
репортят через `ErrorHandler`), либо внутри собственных фоновых задач
перехватывайте и репортите явно:

```python
try:
    await do_something_risky()
except Exception as exc:
    await self.ctx.report_error(exc, event="do_something_risky")
```

## Как устроена горячая перезагрузка

`plugin reload <name>` никогда не делает наивный
`importlib.reload(module)`. Такой подход не трогает уже
зарегистрированные команды/слушатели, не отменяет старые фоновые
задачи и молча плодит дублирующиеся обработчики событий при каждой
перезагрузке. Вместо этого (`core/plugin_manager.py::reload`):

1. **Фаза импорта.** Все записи в `sys.modules` под `plugins.<name>`
   удаляются, и `plugins.<name>.plugin` импортируется заново. Ошибка
   синтаксиса или импорта перехватывается *до того, как работающий
   плагин вообще был затронут* -- старая рабочая версия продолжает
   обслуживать трафик.
2. **Фаза конструирования.** Создаётся экземпляр нового класса плагина.
   Исключение в конструкторе так же полностью изолировано; ничего ещё
   не остановлено.
3. **Фаза замены.** Только теперь останавливается *старый* экземпляр:
   выполняется его собственный `stop()`, затем
   `PluginContext.release()` отменяет каждую запущенную им фоновую
   задачу, отписывает каждый зарегистрированный им слушатель Event Bus
   и удаляет каждый добавленный им cog (а значит, и все
   команды/слушатели в нём). После этого запускаются `setup()`/`start()`
   *нового* экземпляра.
4. **Откат.** Если `setup()`/`start()` из шага 3 выбрасывают
   исключение, менеджер заново запускает `setup()`/`start()` **старого**
   экземпляра со свежим контекстом -- плагин оказывается в точности в
   том состоянии, как будто перезагрузки не было, а ошибка (со
   стабильным ID вида `ERR-...`) репортится в консоль и в Discord-канал
   ошибок.

Это напрямую проверяется в `tests/test_plugin_manager.py` --
перезагрузка с синтаксической ошибкой, с падающим конструктором, с
падающим `setup()`, и чистая перезагрузка со сменой версии -- каждый
тест проверяет отсутствие дублирующихся слушателей, отсутствие
"осиротевших" задач и (для случаев с ошибкой) что старый плагин
по-прежнему полностью работоспособен.

**Что должен гарантировать автор плагина:** всё, что вы регистрируете
через `self.ctx` (cog'и, подписки на события, `self.ctx.create_task(...)`),
освобождается автоматически. Всё, что вы получаете *в обход* `self.ctx`
(например, сами открыли `aiohttp.ClientSession`), освобождайте сами в
`stop()` -- и сделайте `stop()` безопасным для повторного вызова, так
как при откате `setup()`/`start()` могут быть вызваны на том же
экземпляре повторно после того, как он уже отработал один раз.

## Безопасность

- Токен хранится только в `.env` / переменной окружения
  `DISCORD_TOKEN`, никогда не логируется, `.gitignore` уже исключает
  `.env`.
- Весь пользовательский ввод в Message Builder проверяется через
  Pydantic (`services/message_service.py::MessageSpec`) прежде, чем
  дойти до Discord API.
- Каждая команда, изменяющая состояние (`/mod ...`, `/setup ...`),
  защищена проверкой роли из `core/permissions.py` -- никогда не
  захардкоженным ID пользователя/роли.
- На чувствительные/часто вызываемые команды навешен
  `app_commands.checks.cooldown`.
- Исходящие вызовы Discord, которые могут временно падать, идут через
  ограниченный backoff в `utils/discord_retry.py`.

## Что можно добавить дальше

ТЗ явно требует архитектуру, которая растёт без изменений в ядре. Flight
logging, METAR/TAF, тикеты, `/server stats`, XP/репутация, flight
events и авиа-профиль участника уже реализованы (см.
[«Как пользоваться ботом»](#как-пользоваться-ботом)); вот что осталось
за рамками этого этапа:

- **Веб-дашборд** -- настройки, логи и статистика сервера прямо в
  браузере, с авторизацией через Discord OAuth2, чтобы бота можно было
  развернуть сразу на несколько серверов, и на каждом администраторы
  настраивали бы только свой сервер. Технически реализуемо (Discord
  предоставляет OAuth2 + REST API именно для таких сценариев), но
  требует отдельного веб-приложения (backend на FastAPI/аналоге +
  фронтенд), общей с ботом базы данных, разделения `guild_settings` по
  правам доступа конкретного администратора и вынесения текущих
  YAML-конфигов в БД полностью (сейчас часть настроек всё ещё читается
  из `config/config.yaml`, общего для всех серверов). Отдельный,
  самостоятельный по объёму этап работы, а не расширение одного
  плагина -- не делаем, пока не понадобится многосерверный режим.
- **Redis** -- слой сервисов уже отделяет хранение (`database/`) от
  бизнес-логики (`services/`), поэтому добавление слоя кэширования
  позже -- это изменение в `services/`, а не переписывание всего.
  Не добавлено сейчас, потому что пока в этом нет необходимости (ТЗ §38).
- **Дополнительные локали** (`de`, `fr`, `es`) -- положите
  `locales/de.json` рядом с `ru.json`/`en.json`; `utils/i18n.py`
  подхватит его автоматически.

## Частые проблемы

**Бот запускается, база данных подключается, плагины грузятся, команды
синхронизируются -- но бот так и не появляется в сети на сервере
(статус в Discord остаётся серым, участник списка "офлайн").** Это
самая частая причина "бот не стартует": в Discord Developer Portal, на
вкладке **Bot**, не включены **Server Members Intent** и/или **Message
Content Intent**. Без них шлюз Discord отклоняет подключение с кодом
`4014 Disallowed intent(s)` -- и, что особенно обманчиво, делает это
**молча**: никакой ошибки не выбрасывается, бот просто бесконечно
пытается переподключиться на пустом месте. Через 30 секунд после
старта бот сам напишет в лог подсказку про это (`Бот всё ещё не
подключился к Discord...`), если не может подключиться. Исправление:
включите оба переключателя (см.
[«Настройка бота в Discord»](#настройка-бота-в-discord)) -- перезапуск
бота не нужен, следующая же попытка переподключения (в течение
нескольких секунд) сама пройдёт успешно.

**Бот в сети, но не реагирует на `/setup`, `/mod` и другие команды.**
Скорее всего, slash-команды ещё не синхронизировались глобально (это
может занимать до часа после первого запуска). Для мгновенной проверки
укажите `DEV_GUILD_ID` в `.env` (ID вашего сервера) и перезапустите бота
-- команды появятся на этом сервере сразу же.

**В логах не появляются удалённые/изменённые сообщения, входы/выходы
участников.** Проверьте, что во вкладке Bot в Discord Developer Portal
включены **Server Members Intent** и **Message Content Intent** (см.
[«Настройка бота в Discord»](#настройка-бота-в-discord)), и что нужный
канал назначен через `/setup channels`.

**Бот не может забанить/выдать роль конкретному участнику.** Роль бота
в списке ролей сервера должна быть выше роли участника, которым он
пытается управлять -- поднимите роль бота в Server Settings -> Roles.

**Ошибка подключения к базе данных при запуске.** Проверьте
`DATABASE_URL` в `.env` -- формат должен быть
`postgresql+asyncpg://пользователь:пароль@хост:5432/имя_бд`. При
Docker-варианте база поднимается отдельным контейнером `postgres`
автоматически; при ручной установке база и пользователь должны быть
созданы заранее (см. [«Установка на сервер с нуля»](#установка-на-сервер-с-нуля)).

**Как посмотреть, что вообще происходит, если что-то не работает.**
Все ошибки бота автоматически попадают в канал ошибок, настроенный
через `/setup channels`, и в файл `logs/skyhub.jsonl` (в формате JSON,
с ID ошибки, именем плагина и полным traceback) -- путь к этому файлу
показывает консольная команда `logs`. Также можно проверить статус
командой `/status` в Discord или `status` в консоли.
