## Архитектура

Три слоя, зависимости идут в одну сторону:

**Core → Services → Plugins**, а всё взаимодействие между плагинами идёт
через **Event Bus**, а не через прямые импорты друг друга.

```
Discord  <-->  SkyHubBot (discord.py)
                 │
                 ├── PluginManager  ──загружает/перезагружает──>  plugins/*
                 │                                                   │
                 ├── EventBus  <───────публикация/подписка───────────┘
                 │
                 ├── PermissionService, ErrorHandler, I18n, TTLCache
                 │
                 └── Database (SQLAlchemy async) ──> PostgreSQL
```

| Компонент | Файл | За что отвечает |
|---|---|---|
| `BasePlugin` | `core/base_plugin.py` | Единственный интерфейс, который реализует каждый плагин: `setup()` / `start()` / `stop()`. |
| `PluginContext` | `core/plugin_context.py` | Единственный способ, которым плагин взаимодействует с ботом -- каждый cog, команда, подписка на событие и фоновая задача регистрируются здесь, чтобы их можно было автоматически освободить. |
| `PluginManager` | `core/plugin_manager.py` | Обнаруживает, загружает, разрешает зависимости и **безопасно перезагружает** плагины "на лету". |
| `EventBus` | `core/event_bus.py`, `core/events.py` | Асинхронная шина событий (pub/sub). Плагин никогда не импортирует другой плагин напрямую -- он публикует события/подписывается на них (`MemberJoined`, `ModerationAction`, `VoiceCreated` и т.д.). |
| `ErrorHandler` | `core/error_handler.py` | Любое исключение где угодно получает ID вида `ERR-ГГГГММДД-xxxxxx`, попадает в консольный лог и (с ограничением частоты) публикуется embed'ом в канал ошибок Discord. |
| `PermissionService` | `core/permissions.py` | Централизованное определение роли `OWNER > ADMIN > MODERATOR > SUPPORT > MEMBER > USER` -- ни один плагин никогда не хардкодит роль или ID пользователя. |
| `GuildConfigService` | `services/guild_config_service.py` | Определяет "в какой канал/какая роль" -- сначала `guild_settings` (настраивается вживую через `/setup`), затем `config.yaml` как запасной вариант. |
| `Database` | `database/database.py` | Асинхронная фабрика движка/сессий SQLAlchemy. Плагины никогда не держат сессию открытой -- используют `ctx.db.session()` как короткоживущий контекстный менеджер. |

### Почему это не разваливается при 30-50 плагинах

- **Ни один плагин не импортирует другой.** Всё сквозное поведение
  (например, плагин `audit`) строится через подписку на события, которые
  уже публикуют другие плагины -- добавление нового плагина не требует
  правок в существующих.
- **Ни один плагин не трогает `bot.add_cog` / `bot.tree.add_command`
  напрямую.** Всё идёт через `PluginContext` -- именно это делает
  возможной автоматическую горячую перезагрузку без утечек ресурсов, см.
  [Как устроена горячая перезагрузка](#как-устроена-горячая-перезагрузка).
- **Нигде нет захардкоженных ID.** Каналы/роли/категории определяются
  через `GuildConfigService`, настраиваются для каждого сервера прямо из
  Discord командой `/setup`.
- **Баг одного плагина не может уронить другой.** Обработчики Event Bus,
  фоновые задачи и slash-команды обёрнуты так, что исключения
  перехватываются, отправляются через `ErrorHandler` и никогда не
  попадают в основной цикл обработки событий Discord.

## Разработка новых плагинов

Плагин -- это папка внутри `plugins/` с файлом `plugin.py`,
предоставляющим переменную `PLUGIN_CLASS`. Это весь контракт, который
нужен `PluginManager`, чтобы его обнаружить -- без изменений в ядре.

```
plugins/
└── weather/
    ├── __init__.py
    ├── plugin.py        <- обязателен: PLUGIN_CLASS = WeatherPlugin
    ├── commands.py       (опционально) slash-команды
    ├── service.py         (опционально) бизнес-логика, тестируемая без discord.py
    └── config.yaml       (опционально) значения по умолчанию, объединяются с plugins.weather в config.yaml
```

### 1. Минимальный плагин

```python
# plugins/weather/plugin.py
from core.base_plugin import BasePlugin, PluginMeta

class WeatherPlugin(BasePlugin):
    meta = PluginMeta(
        name="weather",
        version="1.0.0",
        description="Получение METAR/TAF",
        author="Ваше имя",
        dependencies=(),          # напр. ("voice_channels",), если есть зависимость
    )

    async def setup(self) -> None:
        # регистрируйте cog'и/команды/слушатели здесь -- всегда через self.ctx
        pass

PLUGIN_CLASS = WeatherPlugin
```

Затем:

```
plugin enable weather
```

### 2. Добавление slash-команды

```python
import discord
from discord import app_commands
from discord.ext import commands

class WeatherCog(commands.Cog):
    def __init__(self, ctx):
        self.ctx = ctx

    @app_commands.command(name="metar", description="Получить последний METAR для аэропорта")
    async def metar(self, interaction: discord.Interaction, icao: str) -> None:
        await interaction.response.send_message(f"METAR для {icao.upper()}: ...")

# в WeatherPlugin.setup():
await self.ctx.add_cog(WeatherCog(self.ctx))
```

Именно `ctx.add_cog` (а не `self.ctx.bot.add_cog`) позволяет менеджеру
плагинов автоматически удалить cog -- и все команды/слушатели в нём --
при перезагрузке/выгрузке.

### 3. Публикация событий и подписка на них

```python
from core.events import Event
from dataclasses import dataclass

@dataclass(frozen=True, kw_only=True)
class MetarFetched(Event):
    icao: str

# публикация (из любого места, где есть доступ к ctx):
self.ctx.emit(MetarFetched(guild_id=interaction.guild_id, icao=icao))

# подписка (обычно в setup() другого плагина):
self.ctx.subscribe(MetarFetched, self._on_metar_fetched)
```

Обработчики изолированы: исключение в вашем обработчике перехватывается,
передаётся в `ErrorHandler` и не влияет на других подписчиков.

### 4. Добавление модели базы данных

1. Добавьте модель в `database/models/your_model.py`, зарегистрируйте её
   в `database/models/__init__.py`.
2. Добавьте репозиторий в `database/repositories/` -- плагины никогда не
   пишут SQL/ORM-запросы сами, только через репозиторий.
3. Выполните `alembic revision --autogenerate -m "add your_model"` и
   проверьте сгенерированную миграцию перед коммитом.
4. Используйте из плагина через `async with self.ctx.db.session() as session:`.

### 5. Горячая перезагрузка

Просто отредактируйте файлы плагина и выполните:

```
plugin reload weather
```

Что именно при этом происходит и что должен гарантировать ваш плагин --
см. раздел [Как устроена горячая перезагрузка](#как-устроена-горячая-перезагрузка).
Практическую сторону ("что можно менять без перезапуска бота вообще") --
см. [docs/DEPLOYMENT.md](DEPLOYMENT.md#обновление-без-полного-перезапуска).

### 6. Обработка ошибок

Не глотайте исключения молча и не позволяйте им ронять слушатель.
Либо дайте исключению всплыть из метода cog'а (discord.py направит его
в общие обработчики `on_app_command_error`/`on_error`, которые уже
репортят через `ErrorHandler`), либо внутри собственных фоновых задач
перехватывайте и репортите явно:

```python
try:
    await do_something_risky()
except Exception as exc:
    await self.ctx.report_error(exc, event="do_something_risky")
```

## Как устроена горячая перезагрузка

`plugin reload <name>` никогда не делает наивный
`importlib.reload(module)`. Такой подход не трогает уже
зарегистрированные команды/слушатели, не отменяет старые фоновые
задачи и молча плодит дублирующиеся обработчики событий при каждой
перезагрузке. Вместо этого (`core/plugin_manager.py::reload`):

1. **Фаза импорта.** Все записи в `sys.modules` под `plugins.<name>`
   удаляются, и `plugins.<name>.plugin` импортируется заново. Ошибка
   синтаксиса или импорта перехватывается *до того, как работающий
   плагин вообще был затронут* -- старая рабочая версия продолжает
   обслуживать трафик.
2. **Фаза конструирования.** Создаётся экземпляр нового класса плагина.
   Исключение в конструкторе так же полностью изолировано; ничего ещё
   не остановлено.
3. **Фаза замены.** Только теперь останавливается *старый* экземпляр:
   выполняется его собственный `stop()`, затем
   `PluginContext.release()` отменяет каждую запущенную им фоновую
   задачу, отписывает каждый зарегистрированный им слушатель Event Bus
   и удаляет каждый добавленный им cog (а значит, и все
   команды/слушатели в нём). После этого запускаются `setup()`/`start()`
   *нового* экземпляра.
4. **Откат.** Если `setup()`/`start()` из шага 3 выбрасывают
   исключение, менеджер заново запускает `setup()`/`start()` **старого**
   экземпляра со свежим контекстом -- плагин оказывается в точности в
   том состоянии, как будто перезагрузки не было, а ошибка (со
   стабильным ID вида `ERR-...`) репортится в консоль и в Discord-канал
   ошибок.

Это напрямую проверяется в `tests/test_plugin_manager.py` --
перезагрузка с синтаксической ошибкой, с падающим конструктором, с
падающим `setup()`, и чистая перезагрузка со сменой версии -- каждый
тест проверяет отсутствие дублирующихся слушателей, отсутствие
"осиротевших" задач и (для случаев с ошибкой) что старый плагин
по-прежнему полностью работоспособен.

**Что должен гарантировать автор плагина:** всё, что вы регистрируете
через `self.ctx` (cog'и, подписки на события, `self.ctx.create_task(...)`),
освобождается автоматически. Всё, что вы получаете *в обход* `self.ctx`
(например, сами открыли `aiohttp.ClientSession`), освобождайте сами в
`stop()` -- и сделайте `stop()` безопасным для повторного вызова, так
как при откате `setup()`/`start()` могут быть вызваны на том же
экземпляре повторно после того, как он уже отработал один раз.

## Тестирование

```bash
pip install -r requirements-dev.txt
pytest
```

  на синтетических плагинах, создаваемых на диске на время теста.

  плагин из `plugins/` через настоящий `PluginManager`, вылавливая

  error-sink, отписка по владельцу.
- `tests/test_permissions.py` -- определение роли (владелец/админ/
  настроенная роль/участник/гость -- цепочка запасных вариантов).
- `tests/test_message_service.py` -- рендеринг Message Builder +
  разбиение на страницы (`MESSAGE i/N`) + поведение "автор только на
  первой странице".
- `tests/test_voice_repository.py` -- сохранение временных голосовых
  каналов (история передачи владения, смена режима, лимит участников)
  на SQLite в памяти, без необходимости в Postgres.
- `tests/test_phase8_repositories.py` -- репозитории авиапрофиля,
  бортжурнала, событий, тикетов, XP.
- `tests/test_manual_channel_select.py` / `test_manual_role_select.py` --
  собственные списки выбора канала/роли в `/setup` (см. «Безопасность и
  аудит» ниже -- замена нативных компонентов Discord).
- `tests/test_moderation_hierarchy.py` -- защита от применения `/mod`
  к участнику с равным/более высоким уровнем доступа.
- `tests/test_edited_messages_self_filter.py` -- бот не логирует правки
  собственных сообщений (живой статус, радио).

## Безопасность и аудит

### Постоянно действующие меры

- Токен хранится только в `.env` / переменной окружения
  `DISCORD_TOKEN`, никогда не логируется; `.gitignore` и `.dockerignore`
  исключают `.env` и из git, и из слоёв Docker-образа.
- Весь пользовательский ввод в Message Builder проверяется через
  Pydantic (`services/message_service.py::MessageSpec`) прежде, чем
  дойти до Discord API.
- Каждая команда, изменяющая состояние (`/mod ...`, `/setup ...`),
  защищена проверкой роли из `core/permissions.py` -- никогда не
  захардкоженным ID пользователя/роли.
- Весь доступ к БД идёт через SQLAlchemy ORM с параметризованными
  запросами -- нигде нет f-строк/конкатенации в SQL, SQL-инъекции
  исключены по конструкции.
- Внешние процессы (`ffmpeg` для радио) запускаются через
  `subprocess.Popen` со списком аргументов, без `shell=True` --
  командная инъекция через имя файла невозможна.
- На чувствительные/часто вызываемые команды навешен
  `app_commands.checks.cooldown`.
- Исходящие вызовы Discord, которые могут временно падать, идут через
  ограниченный backoff в `utils/discord_retry.py`.
- Пользователю никогда не показывается сырой traceback -- только
  стабильный `error_id`; полный traceback уходит в лог и в
  Discord-канал ошибок, настроенный администратором.

### Осознанно не тронуто (компромисс, не баг)

- **`/event create` не требует особой роли** -- любой участник сервера
  может создать карточку совместного вылета. Оставлено как есть,
  поскольку это по духу открытая функция сообщества (ТЗ: "совместные
  вылеты сообщества"), а не административная -- как `/message`/`/embed`.
  Если нужно ограничить (например, ролью `MEMBER` с проверкой стажа
  или кулдауном на количество событий в день), это несложно добавить
  отдельным изменением.
- **Иерархия в `/mod`** блокирует действие и между двумя участниками
  с *одинаковым* уровнем (например, два модератора) -- осознанно
  консервативный выбор по умолчанию. Если на сервере ожидается, что
  модераторы могут санкционировать друг друга, это одна строка правки
  в `ModerationCog._check_hierarchy` (сравнение `>` вместо `>=`).
- **Владелец сервера теоретически мог настроить пароль Postgres по
  умолчанию** (`skyhub`, см. `docker-compose.yml`) -- порт базы не
  публикуется наружу (виден только контейнеру бота), поэтому внешняя
  эксплуатация невозможна без отдельного компромисса хоста. Тем не
  менее в `.env.example` добавлена переменная `POSTGRES_PASSWORD` --
  рекомендуется задать свою на любом сервере, который не полностью
  изолирован.

## Что можно добавить дальше

ТЗ явно требует архитектуру, которая растёт без изменений в ядре. Flight
logging, METAR/TAF, тикеты, `/server stats`, XP/репутация, flight
events и авиа-профиль участника уже реализованы (см.
[Команды бота](COMMANDS.md)); вот что осталось за рамками этого этапа:

- **Веб-дашборд** -- настройки, логи и статистика сервера прямо в
  браузере, с авторизацией через Discord OAuth2, чтобы бота можно было
  развернуть сразу на несколько серверов, и на каждом администраторы
  настраивали бы только свой сервер. Технически реализуемо (Discord
  предоставляет OAuth2 + REST API именно для таких сценариев), но
  требует отдельного веб-приложения (backend на FastAPI/аналоге +
  фронтенд), общей с ботом базы данных, разделения `guild_settings` по
  правам доступа конкретного администратора и вынесения текущих
  YAML-конфигов в БД полностью (сейчас часть настроек всё ещё читается
  из `config/config.yaml`, общего для всех серверов). Отдельный,
  самостоятельный по объёму этап работы, а не расширение одного
  плагина -- не делаем, пока не понадобится многосерверный режим.
- **Redis** -- слой сервисов уже отделяет хранение (`database/`) от
  бизнес-логики (`services/`), поэтому добавление слоя кэширования
  позже -- это изменение в `services/`, а не переписывание всего.
  Не добавлено сейчас, потому что пока в этом нет необходимости.
- **Дополнительные локали** (`de`, `fr`, `es`) -- положите
  `locales/de.json` рядом с `ru.json`/`en.json`; `utils/i18n.py`
  подхватит его автоматически.
